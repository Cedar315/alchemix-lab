# Cocktail Agent + RAG：智能调酒助手实施与测试方案

更新日期：2026-09-12。

**项目必须包含 AI Agent 与 RAG 两个可运行、可分别评估的模块。** 核心任务：根据用户材料和口味，自主查询配方、检索调酒知识、检查制作条件，推荐可制作的酒，并回答制作中的问题。

本文描述目标方案。现已实现 RAG 入库、向量检索、MiniMax 证据问答后台和管理员测试台，离线测试已通过；真实服务配置、数据库迁移及端到端验证尚未完成。Agent 工具循环尚未实现。配置步骤见 [RAG 后台说明](rag-setup.md)。

## 1. 产品入口与第一版范围

保留现有首页问卷、材料选择、三杯推荐与逐杯更换功能。

- “已有材料”选完后增加“让助手帮我选”，进入对话页面。第一版使用用户本次明确选择的材料，不依赖个人酒柜先完成。
- 用户可输入“清爽一点，不要太甜”，也可使用快捷选项。
- 助手展示酒名、材料用量、制作步骤、简短推荐理由、知识来源，以及“开始制作”“换一杯”。用户明确只要一杯时返回一杯，不强制返回三杯。
- 配方详情页提供继续提问入口，自动携带当前配方上下文。
- 工具执行状态可简要展示“查找配方”“检查材料”“查阅资料”；调试视图保存结构化调用记录，不展示模型私有推理过程。

第一版必须实现 Agent、RAG 和测试。个人酒柜、历史偏好、天气、待制作计划属于后续扩展；它们不阻塞第一版验收。

## 3. AI Agent 模块（必需）

### 3.1 定义与职责

Agent 由语言模型、工具注册表、执行循环和状态管理组成。模型根据用户需求选择工具，读取工具返回值，再决定查询、追问、重试或回答。不能仅在界面播放固定步骤，也不能把一次提示词生成叫作已实现工具 Agent。

模型负责理解意图、选择工具和解释结果；普通代码负责权限、输入校验、材料约束、执行上限和最终结果校验。

### 3.2 第一版工具

| 工具 | 输入 | 输出 |
| --- | --- | --- |
| `find_recipes` | 口味、酒味偏好、用户材料、排除项、工具条件 | 候选配方 ID、完整必需材料及用量、制作方法。只返回真实配方记录。 |
| `check_recipe` | 配方 ID 或结构化配方、材料数量、工具信息 | `pass / fail / needs_info`、缺料、数量不足、未知信息及步骤问题。 |
| `search_knowledge` | 调酒问题、当前配方与必要材料上下文 | RAG 检索返回的知识片段、条目 ID、来源、相关性分数和适用条件。 |

第一版优先检索已有配方。若提出调整，必须重新调用 `check_recipe`。数量未知不视为足量；缺少糖浆、冰或工具时不能默认存在。

### 3.3 执行循环

```text
用户请求 + 本次材料 + 当前配方/对话状态
                ↓
模型选择下一步：调用工具 / 追问 / 回答
                ↓
服务端验证工具名、参数和权限 → 执行工具
                ↓
结果写回当前任务状态
                ↓
缺料或信息不足 → 换候选或追问 → 继续循环
                ↓
最终校验通过 → 输出配方、解释和引用
```

调酒知识问题可以只调用 `search_knowledge`；不强制每轮调用所有工具。推荐任务在最终输出前必须经过代码校验；直接知识库命中可走快捷回答，但该路径单独标记，不作为 Agent 工具循环完成的证据。

初始执行限制建议：每轮最多 6 次工具调用、总时限 30 秒，并设置输出及费用预算。实际阈值根据延迟和测试调整。超限或工具失败时给出已有可靠结果或追问，不编造工具成功。

记录 request ID、模型版本、工具名、已脱敏参数、结果状态、重试、耗时、token 用量与引用 ID。工具不可执行任意 SQL；用户身份由服务端确定，不接受模型指定他人 userId。

## 4. RAG 模块（必需）

RAG 使用检索到的调酒资料支撑生成回答。必须实际实现检索与上下文注入，不只把几条常识写进系统提示词。

### 4.1 知识入库

可靠来源收集 → 人工/规则审查 → 按完整知识点拆分 → 保存来源与版本 → 生成 embedding → 写入索引。

每条知识保留：ID、问题及别名、正文、分类、适用条件、来源链接、核查日期、审查状态、证据类型、版本。切分时不得把结论与例外条件拆散。AI 新生成内容进入待审队列，不自动升级为可信知识。

第一批 12 条包含：气泡摇和、稀释、重复用冰、碎玻璃、糖浆浓度、计量、橙味利口酒、汤力、生蛋、酒味与酒精含量、莫吉托缺料、分层。来源已初步核对，不等于专业试做认证，也不足以覆盖完整问答范围。

### 4.2 检索与生成

```text
用户问题 + 当前配方上下文
          ↓
材料别名归一化、主题识别
          ↓
关键词检索 + 向量检索
          ↓
结果合并、去重、相关性排序
          ↓
取少量相关片段并保留适用条件
          ↓
AI 根据片段回答 → 校验来源 ID → 展示回答和引用
```

技术方向：优先评估现有 Supabase/Postgres 加 pgvector。实施前确认扩展可用性、embedding 模型和向量维度；检索层使用统一接口，便于替换实现。第一版包含向量检索，关键词/别名检索用于补足精确材料名。

先以 Top-3 至 Top-5 为可调范围，通过开发集确定阈值与条目数量。相似度分数不是答案正确概率，不能仅凭高分保证结论可靠。

### 4.3 知识库优先与降级

- 明确命中经审查的单一问题：允许直接返回知识答案和来源，标记 `knowledge_direct`，节省模型调用。
- 部分匹配、需要结合配方或多问题：把资料交给模型整理，标记 `rag_answer`。
- 无可靠资料：优先追问；一般调酒问题若使用模型补充，要明确无知识库依据，标记 `ai_fallback`，不伪造引用。
- 食品安全、过敏、药物、变质等问题证据不足时，不提供确定保证。
- 引用仅接受本轮检索返回的来源 ID，链接由服务端解析。检索文本作为资料处理，不可覆盖系统规则或触发任意工具操作。

## 5. 两个模块如何配合

用户：“我有伏特加、橙汁和苏打水，想喝清爽一点的。”

1. Agent 解析口味、现有材料和推荐数量。
2. 调用 `find_recipes` 查候选。
3. 调用 `check_recipe` 检查材料、数量、冰和工具。未知则追问，失败则换候选。
4. 按需要调用 `search_knowledge`，获取对应制作方法、替代边界等资料。
5. 对最终配方再做代码校验，输出实际可做的酒及来源；信息未确认时列出待确认项。
6. 用户追问“能一起摇吗”，Agent 携带当前配方调用知识检索，再给针对性回答。

RAG 提供知识依据，Agent 决定如何使用工具完成任务。两者可独立运行与测试，再做集成评估。

## 6. 效果测试（必需）

### 6.1 先建立固定测试集

建议第一批建立约 60 个案例：20 个知识问答、20 个材料推荐、10 个缺料或多轮修改、10 个无依据与工具失败案例。数量为起点，不代替覆盖率检查。

每个案例包含输入、材料/工具上下文、预期引用或相关条目、必守约束、允许答案范围、预期工具行为和成功标准。开发集用于调提示词、检索参数；保留独立测试集，不用其答案反复调参。

例子：

| 案例 | 期望 |
| --- | --- |
| 用户没有金酒 | 不得把需要金酒的配方标记为可制作。 |
| 用户有材料但数量未知 | 不声称用量足够，明确待确认。 |
| 用户不喜欢奶味 | 不推荐含奶味材料的配方。 |
| 君度和橙味利口酒的关系 | 找到对应来源，回答准确并引用。 |
| 多个饮料缺货 | 更新排除条件，重新校验，不循环返回同一缺料配方。 |
| 知识库没有可靠回答 | 不编造来源或假装检索命中。 |
| 配方查询或模型超时 | 正确降级，不声称工具成功。 |
| 只生成了一杯推荐 | 不自动创建真实饮酒记录。 |

### 6.2 分层指标

| 层次 | 主要指标 |
| --- | --- |
| RAG 检索 | Recall@K（标注相关条目被找回的比例）、MRR（首个相关条目的排名）、无答案问题的错误命中率。 |
| RAG 回答 | 人工核验的事实正确性、对证据的忠实度、引用是否支持相邻结论、无依据时的正确降级。 |
| Agent | 任务完成率、材料/工具违规率、调用参数合法率、缺料后恢复成功率、循环超限率。 |
| 用户体验 | 选定配方和完成制作的比例、操作困难、推荐满意度；好喝程度需要真实试做反馈。 |
| 性能与成本 | P50/P95 延迟、每次成功任务的模型与检索费用、工具调用次数。 |

记录工具执行事实，不要求或收集模型私有思维链。自动校验判断硬约束，人工评审判断答案依据和实用性；不能只让另一个模型打分。

### 6.3 对照实验

| 版本 | 配置 | 目的 |
| --- | --- | --- |
| A：仅 AI | 相同模型与用户上下文，不检索知识，不使用工具循环 | 基线。 |
| B：AI + RAG | 加知识检索，固定问答/推荐流程 | 对比 A，观察证据与知识准确性变化。 |
| C：Agent + RAG + 校验 | 自主工具调用、检索、重新选择与硬约束校验 | 完整产品效果。 |
| D：固定流程 + RAG + 同一校验器 | 与 C 使用相同配方库、知识库、工具与校验，但固定调用顺序 | 对比 C，区分 Agent 调度的增益与校验器本身的增益。 |

在相同案例、数据快照和模型版本上比较，记录每组差异。知识问答任务和推荐任务分开统计；对存在随机性的任务重复运行。不能预设 Agent 一定更好。未校验的基线只用于离线实验，不直接向真实用户宣称配方可做。

### 6.4 第一版验收标准

- 能真实调用三个工具，并展示缺料后换候选或追问的测试轨迹。
- RAG 能检索知识片段、生成有依据的回答并显示真实引用。
- 固定测试集的材料、排除项和身份隔离等硬约束案例全部通过；测试通过不等于所有未来输入绝对安全。
- 无命中、无候选、超时和重复请求均有明确处理。
- 输出可复现的测试结果，记录版本、配置、样本量与未解决问题；质量和延迟数值目标在首次基线测量后制定。

## 7. 实施顺序

1. 定义结构化输入输出、工具接口和测试集。
2. 扩充并审查知识，完成 embedding、检索、引用和独立 RAG 问答。
3. 完成 Agent 执行循环，接入 `find_recipes`、`check_recipe`、`search_knowledge`，加入执行上限和日志。
4. 接入已有材料后的助手页面与配方追问入口，跑通端到端测试。
5. 完成 A/B/C/D 对照实验和小白使用测试，据此优化。
6. 再建立个人酒柜、历史偏好与待制作计划。

个人酒柜应记录材料 ID、品牌、剩余量、单位和最近确认时间；未评分不当作低分，少量低分只作弱偏好。天气可选，不应成为第一版必需依赖。

推荐可以保存到“今晚想做”，但用户明确确认制作或饮用后才能写入真实记录。现有 `DrinkLog.isFinished` 默认 true，不直接用推荐事件调用记录接口。后续写入使用幂等键，库存更新与记录保持一致。

## 8. 开发与部署约定

继续在本地改版分支实现、预览和测试；用户验收后统一推送。文档中的模型、向量存储和阈值属于实施方向，接入前核对兼容性与费用，不把尚未验证的服务描述成已完成能力。
