# 实施路线图与发布门槛

> 历史记录：保留当时的设计、结果及限制，不代表当前实现。当前版本见 [文档导航](../README.md)。

更新：2026-09-14。文档修订先行；悬浮助手主路径已接入，具体代码和验证见 [实现说明](companion-implementation.md)，不以局部通过代表全部路线图完成。

## 1. 当前基础

已有工作流页面、独立制作问答、RAG、身份校验、共享配额与部分验证脚本。已有基础仍需针对新方案复用验证，尤其是多套配方数据、具体详情路由和页面操作能力。

## 2. 实施顺序

| 阶段 | 交付物 | 完成门槛 |
| --- | --- | --- |
| 0 需求与文档 | 产品概述、功能交互、AI生成策略、回复模板、两张流程图、场景验收及操作手册 | 已完成文档修订与静态校验；功能状态见实现说明 |
| 1 复用能力审计 | 页面／功能／数据源／匹配函数／路由映射，配方质量清单 | 两类真实候选均可验证，不依赖旧六杯目录 |
| 2 受控工具与任务状态 | 匹配适配器、页面能力注册表、意图协议、上下文来源与隔离 | 三杯上限、类别条件、过期动作和跨杯污染测试通过 |
| 3 入口与统一交互 | 三处浮窗、移动抽屉、导航与预填、覆盖确认、视觉组件统一 | 不抢主流程；真实详情与实验室交接通过 |
| 4 知识和评估 | 场景缺口补充、独立用例、真实集成、人工引用评审 | 核心验收无阻断问题，失败路径可恢复 |
| 5 发布与观察 | 配置／索引一致性、可关闭入口、任务事件、问题分组 | 工作流不受助手异常影响，指标可计算 |

阶段1发现工作流本身没有能力时，先决定是否补工作流，再接助手；不能在 Agent 内临时复制一套业务逻辑。视觉统一与助手接入可以在同阶段规划，但需要分别验收。

## 3. 保留与退役

迁移期间保留 `/ask` 兼容路径及已有问题上下文入口；新浮窗通过后再决定重定向或退役。历史 Agent 代码与脚本明确标注 legacy，清理需检查引用和测试，不能仅改文档宣称已经删除。

首版不做 sub-agent、跨设备记忆、自动记录与库存管理、自创配方。增加 sub-agent 的前提是出现可独立验收的专业任务，并证明隔离收益超过额外延迟、成本和故障面。

## 4. 主要依赖与决策

配方质量影响推荐可信度；稳定身份影响详情跳转；结构化上下文影响追问和替换正确性；知识覆盖影响回答范围；完整埋点影响产品价值证明。这些依赖必须先于“做一个聊天窗口”的视觉完成判断。

验收依据：[PRD](prd.md)、[完整流程](preparation-agent.md)、[回复规范](agent-response-guidelines.md)、[验证方案](agent-verification.md)。本轮在已确认文档基础上实现悬浮助手、v2协议和共享工作流适配；没有新增数据库迁移。

后续实现以需求编号、意图场景、展示模板及验收用例对应交付。主路径已接入不等于阶段4人工评审或阶段5业务监测全部完成；历史结果仍只归属于原版本。
