# L2 共享任务信息修复

> 历史记录：保留当时的设计、结果及限制，不代表当前实现。当前版本见 [文档导航](../README.md)。

本轮将 taskState 作为所有 pending 类型的可选公共字段，兼容已有 v2 请求，不新增数据库字段。事实含用户来源、精确/估计/未知标记，记录目标、配方作用域、当前待答字段与对话行为。

- `task-state.ts`：公共信息合并、未知只作用于当前字段、配方和新任务隔离。
- `companion-contract.ts`：所有 pending 类型共享 taskState 协议。
- `companion.ts`：公共状态生命周期；工具检索获得 mergedTaskState；未知字段不再反复追问或删除已有信息。
- `intent-funnel.ts`：L1 识别调整请求，随后交给 L2 状态处理，移除路由前的调整拦截。
- `adjustment.ts`：保存跨轮用量、识别估计表达、澄清总量/额外量、核对标称配方和制作状态。删除固定按10%添加水的逻辑；只有确定的总量才能带入实验室核对，操作不自动增加材料。
- `task-state.test.ts`、`conversation-repair.test.ts`、`companion.test.ts`：公共状态、跨轮、未知、纠正、配方隔离及截图回归。

验证重点：大概40毫升烧酒 → 总量/额外量追问 → 不确定（保留40估计值）→ 总共（核对配方45ml，不能直接认定倒多）。排障中已知材料不会因为操作步骤“不确定”而丢失。

边界：目前采用保守规则识别对话行为，不保证覆盖所有自然语言表达；“不是X，是Y”保留用户纠正原文，业务分支仍需解读。材料替换和排障既有专用流程保留，共用信息层负责保存与传递。当前不提供新的精确补救公式；资料不足时不能伪造建议。会话仍只保留同页内存，刷新开始新会话。

后续边界修复：公共信息合并不能把原始回复直接作为枚举字段的有效值。amountMeaning / mixingStage 由业务校验后确认；用户在追问中补充另一项用量时只增加事实，不跳过未回答的问题。新增连续六轮回归验证：烧酒60ml → 苏打水120ml → 总共 → 我用的是杯子 → 已经混合了，只有最后一步才允许把确认的用量带入实验室。面向用户的已知事实摘要改为中文标签。
