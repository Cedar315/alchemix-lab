# 管理后台指标核查与测试方案

> 历史记录：保留当时的设计、结果及限制，不代表当前实现。当前版本见 [文档导航](../README.md)。

更新说明：后台 Agent 测试入口现已切换到新版运行器（见 [后台说明](../admin-console.md#当前-agent-测试入口2026-10-12)）。下文关于旧版测试入口的核查结论记录的是改造前状态；新版线上采集缺口仍待后续处理。

核查日期：2026-10-12。依据本地代码、数据库迁移和管理文档；未查询线上数据库、未登录线上后台、未执行付费模型评测。这里描述的是实现能力，不是线上指标结果。本次 `npm run test:admin` 的 5 项单元测试通过，仅覆盖指标辅助函数。

## 先修正测量对象

本项目是调酒助手，截图中的“员工自助、人工工单”属于企业服务场景。目前没有工单或人工接管闭环。建议业务主指标先使用“用户反馈解决率”，搭配反馈覆盖率；真实业务结果可观察制作记录，但现有 AI 后制作只是时间关联，不能宣称由 AI 带来。

代码中有三个影响解读的问题：

1. `src/app/api/admin/evaluate/route.ts` 的 Agent 模式调用旧版 `runCompanion`；`src/app/ask/page.tsx` 默认流式模式，`src/app/api/agent/route.ts` 对 messages 请求调用新版 `handleAgentChat`。后台 Agent 通过不能证明新版通过；实际部署是否设置 legacy 尚未核实。RAG 模式仅验证知识子流程，也不代表完整 Agent。
2. 新版 `src/lib/agent-next/route-handler.ts` 写入耗时、回答文本、工具摘要等，但未向 `recordTurn` 提供 knowledge、引用或意图诊断。`queries.ts` 依赖 `rag_status` 统计 RAG，故新版的 RAG 使用、证据不足等会漏计；零值不能解释为没有发生。页面“返回有引用回答”使用 RAG 数减证据不足数，也未逐条验证引用。
3. 新版在流结束回调记录请求；鉴权、校验、额度失败等前置退出不写入同一记录，回调读取结果或写入失败也可能漏记。当前 P95 是已记录请求耗时，不能代表所有请求或用户看到首字的时延。

## 指标逐项定义

所有比例同时显示分子、分母、未评数量与覆盖率。无分母显示“暂无数据”，不显示 0%。生产、内部使用、离线评测分别统计。线上采用 UTC 时间窗口；离线按固定评测批次和版本比较。

| 指标 | 当前能力与查看位置 | 建议口径与补充数据 |
| --- | --- | --- |
| 人工工单减少率 | 未实现，缺工单源及基线 | 有真实人工支持后，以每百个符合条件任务的人工工单数为基准：1−实验组工单率/对照组工单率。同类任务随机分组更适合判断因果；仅前后比较需披露流量、问题难度和人员变化。基线为零时不可计算。 |
| 员工自助解决率 | `/admin/agent` 有用户反馈解决率，可作局部代理 | 当前为 solved/(solved+unsolved)，分母仅已反馈、期间创建的页面任务。另报反馈任务数/总任务数。若要称为“自助解决”，需明确独立任务、人工介入事件与固定观察窗；新请求清空旧反馈，现有值会随任务继续变化。 |
| 平均解决时长 | 未实现；现有 elapsed_ms 是请求耗时 | 增加 task_started_at、resolved_at、resolution_source、reopened_at。对已解决任务计算 resolved_at−started_at 的均值、P50/P95，同时展示未解决比例和等待时长。反馈接口未保存独立反馈时间，不能拿 updated_at 代替解决时间。 |
| Recall@K | 页面无自动汇总；`npm run eval:rag -- test` 已计算 Recall@3/MRR | 为每个可回答问题标注相关证据 ID 集合 G，记录排序后的检索结果 R，单题为 |G∩R前K|/|G|，再按题平均。无相关证据题单列误召回率。现有脚本请求失败的 recall 缺失会被均值排除，须同时报告失败数和有效覆盖率；仅检索测试中的有效题失败可按 0 计，生成失败不要反推检索失败。 |
| 答案正确率 | `/admin/evaluations` 可人工 pass/fail/pending，无独立正确率指标 | 明确必答要点、不可出现的错误和适用范围。正确/已审核可回答题，同时报审核覆盖率、技术失败率。完整服务通过率另以全部计划执行的可回答题为分母，避免剔除失败后虚高。当前单个 grade 是综合评价，不能同时当作多个质量分数。 |
| 引用准确率 | 可在 RAG 测试查看 claims/evidenceIds/citations，无自动语义评分 | 人工判断“论断—引用”是否真的支持：支持的引用关系数/已审核引用关系数。另报需证据论断的引用覆盖率。ID 存在或链接可打开不代表支持论断；无引用时准确率不可计算，不应记为满分。 |
| 拒答准确率 | 有范围外、证据不足案例，未形成混淆矩阵 | 标注应回答/应拒答，信息不足应追问另列。至少显示正确拒答/所有拒答、正确拒答/应拒答、错误拒答/应回答。超时、错误、额度限制不算正确拒答。 |
| 满意度 | 只有 solved/unsolved，未采集满意度 | 单独增加 1–5 分 CSAT；满意度=(4分+5分)/有效评分数，另报评分覆盖率。与是否解决分开，未评分为未知。 |
| P95 响应时延 | `/admin/operations` 已有；总览也展示 | 当前 SQL 使用 percentile_cont(0.95)，来源 pm_turns.elapsed_ms。补充服务端首次输出、全响应完成、浏览器首字与渲染完成时间；按流式/旧版、模型、工具、成功/失败拆分。对超时/取消单列，避免只看成功样本。 |
| 越权访问率 | 有 requireAdmin、RLS 和鉴权验证脚本，无汇总指标 | 区分“被拒绝的访问尝试”与“实际违规放行”。攻击测试违规放行率=实际返回未授权数据或完成未授权操作的案例数/有效攻击案例数。线上另记录授权决策、资源和角色，不收集密钥。403 不算越权成功；只看 HTTP 状态也不够。 |
| 知识更新时效 | 有知识审核、索引维护、版本与操作记录，无端到端时效 | 分别记录 source_changed_at、approved_at、indexed_at、verified_retrievable_at，计算源变更到新内容实际可检索的延迟。无法获得源更新时间时，只能报告审核到生效时间。updated_at 或 attempt 审计不证明生效；保留失败/待生效队列及最老等待时长。 |

## 现在如何查看和测试

1. 打开 `/admin/agent`：选“正式用户”及最近 7 天，读反馈解决率、已反馈/未知数量和未解决原因；自己使用管理员账号的记录要切换“内部使用”。点开请求看上下文，标记值得复测的案例。一个页面任务可能包含多个意图，不能当成已严格去重的业务问题。
2. 打开 `/admin/operations`：查看 P95、请求量、异常数量、模型/版本平均耗时。先确定采集覆盖，再作版本比较。现有总体 P95 混合版本，只能作为概览。
3. 打开 `/admin/evaluations`：选择“仅检索”，测试问题后检查 result 中 hits 的 ID 与排序；切到“RAG 检索并回答”，检查论断与引用，填写人工依据。Agent 模式暂时明确作为旧版测试。当前内置 5 条案例仅够冒烟检查。
4. 用人工评价备注暂存统一结构，例如 `answer=pass; citation=fail; refusal=NA; reason=第二条论断无对应证据`。单个综合 grade 只表示整条人工判定；结构化汇总字段属于后续改造，不会因填备注自动生成图表。
5. 同案例、同模式、同输入比较两个版本。页面历史只取最近 100 条，没有完整按批次统计；不要把这个列表当全量样本。脚本 `npm run eval:rag -- test` 可生成 `artifacts/evaluations/rag-*.json`，调用真实服务并可能产生费用，本次未执行。它的 pass 是状态/召回/引用 ID 规则通过，不是语义正确率。
6. `/admin/knowledge` 审核发布后，到 `/admin/rag/test` 查询目标知识，并验证引用确实来自新版本；同时测试撤回后不可再检索。应在隔离测试知识集进行，避免为了验证改动正式内容。

## 建议评测设计

先建一批 60 题的起步集：30 题可回答（含同义表达、多证据问题）、10 题知识缺失或超范围、10 题需要追问、10 题越权或提示注入。此数量是启动建议，不是统计可靠性保证；各类分别报告，不能用混合通过率掩盖小类别失败。权限测试另外覆盖未登录、普通用户、管理员及用户 A/B 的资源归属。

每题保存 case_id、题目、完整上下文、预期行为、必答要点、相关证据 ID、类别、测试集版本。每次运行保存 batch_id、runtime、代码版本、模型、提示词版本、知识版本、检索配置、输出、耗时及错误。质量标签分别保存 answer_correct、citation_supported、expected_refusal、actual_refusal、reviewer、reviewed_at。

开发集用于调优，保留独立测试集；不要根据测试集失败反复调优后仍称独立评估。发布前运行同一批测试并逐条比较，记录所有重跑。首轮人工审核全部题，后续抽取有代表性的生产样本与失败案例，分别报告，避免只审容易题或只审失败题。待审不当作通过。

权限测试重点：普通用户访问管理页面及 API；用户 A 读取/修改 B 的酒记、收藏和反馈；直接访问未授权表；在提示词或知识文本中要求绕过权限。成功标准同时检查响应体和实际数据变化。没有测试发现不代表全面证明安全。

## 改造顺序与页面设计

1. **先确保采集可靠**：后台增加当前流式 Agent 测试模式，与真实运行器复用；保留旧版作为明确选项。补齐新版 RAG 状态、检索命中、引用、意图及前置失败采集，区分运行器版本。
2. **补 AI 评测汇总**：测试页增加固定数据集、批次、分维度人工标注、Recall@K、正确率、引用与拒答混淆矩阵。保留逐题证据、失败、待审和同批版本差异。
3. **补体验与安全**：运行页展示首字/全响应 P95、记录覆盖率、授权测试结果；知识页展示更新到实际检索生效的时长与未生效队列；用户端独立采集 CSAT。
4. **再补业务闭环**：定义独立任务与解决事件；若确实引入人工服务，再接工单、人工接管及对照基线。未接入前显示“未采集”，不要用请求成功率替代业务收益。

第一轮不承诺任意正确率或延迟目标；先测真实基线，再按使用场景确定目标。权限违规放行可设为发布阻断条件，但“测试集中为零”应附测试范围，不能宣传成系统绝无越权。
