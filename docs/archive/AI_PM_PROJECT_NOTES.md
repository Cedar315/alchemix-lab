## 1. 项目一句话介绍

AlcheMix Lab 面向在家调饮的成年新手，解决“手头材料能做什么、缺料怎么处理、制作中遇到问题怎么办”的决策与操作困难。产品以真实酒单、材料筛选和调配实验室为基础，在配方详情与实验室中提供 AI 调酒伴随助手，将自然语言需求转化为找酒、查知识和进入实验室等受控任务。适合使用 AI 的部分是理解口语、追问和结合证据解释；配方身份、计算、跳转和状态有效性则交给确定性规则。

依据：[README](../../README.md)、[PRD](prd.md)、[伴随助手实现](companion-implementation.md)、[当前编排器](../../src/lib/agent/companion.ts)。当前是有实现和验证记录的项目/MVP，不应表述为已有规模化线上用户。

## 2. 用户场景与 MVP

### 用户与场景

- 核心画像：材料、工具和调酒经验有限，希望按现有条件做出一杯饮品的成年新手。这是产品定位，不是经定量用户研究验证的分群。
- 预期高频场景：按手头材料找酒；查看配方并开始制作；缺少某种材料时判断替代或换酒；连续询问当前这杯酒的做法；对过酸、过烈、没气泡等问题求助。
- 其他产品流程：实验室调整材料和用量、查看计算结果、记录饮用体验。不要把这些普通交互与规则计算全部算作 AI。

### MVP 边界

| 类型 | 当前能力 | 划分理由 |
| --- | --- | --- |
| 普通产品/规则 | 真实酒单、材料匹配、详情、实验室、记录；确定性配方身份与链接 | 结果可验证，不需要模型重新生成既有事实 |
| AI 理解 | 规则未覆盖的意图交给 LLM，以 Tool Calling 返回结构化决策 | 处理口语和表达差异，同时约束可执行范围 |
| Agent 编排 | 待补信息、多轮续接、任务切换、取消、纠错、动作交接 | 用户问题常常不能一轮完成，需要记住“正在解决什么” |
| RAG | 本地知识检索、证据约束回答、受限联网补充、待审知识 | 调酒判断需要依据，不能只依赖模型记忆 |
| 当前不应宣传 | 自动完整代做、任意开放网页操作、多模态识图、成熟个性化长期记忆 | 没有相应的当前主链路实现或验证 |

助手入口并非所有页面通用：当前主要挂载于经典/便利店配方详情及实验室。OCR 接口为未开放状态；若历史文件保留旧 AI Prompt，不代表对应能力仍可用。依据：[AssistantProvider](../../src/components/assistant/AssistantProvider.tsx)、[AI 服务设计](ai-service-design.md)、[路线图](mvp-roadmap.md)。

## 3. Agent 架构

### 真实架构定位

当前 v2 是“规则优先的任务路由 + 原生 Tool Calling + 显式对话状态 + 受控业务执行”的轻量 Agent。它不只是单轮聊天，但也不是自主规划、反思、多 Agent 协作的通用系统；多数确定性问题甚至无需调用意图模型。

| 环节 | 实现及产品含义 | 依据 |
| --- | --- | --- |
| 入口 | 登录鉴权、输入 Schema、请求预算、超时；`version: 2` 进入伴随助手，其他有效旧协议进入 preparation | [API route](../../src/app/api/agent/route.ts) |
| 规则/Router | 取消、实际制作问题、明确酒名、按材料找酒、风味探索等规则；再处理待续接任务；最后才交模型 | [intent-funnel](../../src/lib/agent/intent-funnel.ts)、[companion](../../src/lib/agent/companion.ts) |
| 前置快捷处理 | 调整用量、特定健康知识可在一般漏斗前处理；这也可能造成规则优先级冲突 | [adjustment](../../src/lib/agent/adjustment.ts)、[health-knowledge](../../src/lib/agent/health-knowledge.ts) |
| LLM | MiniMax 兼容接口绑定 Tool Schema，要求一次返回一个 Tool Call，解析为内部 Decision | [provider](../../src/lib/agent/preparation-provider.ts)、[tools](../../src/lib/agent/companion-tools.ts) |
| 上下文 | 页面种类、配方 ID、材料/要求、近期对话、pending、taskId、version | [contract](../../src/lib/agent/companion-contract.ts)、[session](../../src/lib/agent/companion-session.ts) |
| 多轮续接 | 待选类别、缺料/替代、核对配方、实际材料、实际步骤等显式阶段 | [consultation](../../src/lib/agent/consultation.ts) |
| 用户纠错 | 根据当前配方重新核实材料要求；从用户表达中提取替代候选和实际制作事实 | 同上、[recipe-requirements](../../src/lib/agent/recipe-requirements.ts) |
| 取消/切换 | 取消请求、清理待续接状态、版本递增；页面任务变化后旧响应和按钮失效 | [AssistantProvider](../../src/components/assistant/AssistantProvider.tsx) |

### 为什么不全部发给 LLM

明确点名某杯酒、取消操作、固定入口跳转、真实配方匹配、旧动作有效性，都有确定答案。先规则处理可以避免模型把找酒误判为创作、重复追问、生成不存在的配方，也减少不必要调用；目前没有 A/B 或成本数据证明具体节省比例。

需要 LLM 的是规则无法可靠覆盖的口语意图、复杂表达及基于检索证据的解释。Router 的 L1/L2 是规则和待续接处理，不是训练出来的多级分类器；L3 才是模型。

### 状态管理能做到与做不到什么

- 同一杯酒可以续接缺料、材料补充、制作步骤等问题，不必每轮重述全部背景。
- 服务端会重新解析经典/便利店配方的真实目录信息，不把客户端传来的配方文字直接当成官方事实；实验室则是用户草稿。
- 前端用 `taskId + version` 检查异步结果和按钮是否仍适用；停止、改页、更新上下文可让旧结果失效。请求历史最多携带 12 条，界面保留窗口与此不同。
- `recipeKey` 防止把上一杯的咨询状态直接套到下一杯；取消后历史截断可减少旧任务续接。
- 局限：不是服务端持久化会话/授权系统；同页近期历史仍可能影响偏好判断，`new_task` 不等于把全部历史事实彻底清空，也没有完备的事实溯源图。
- 对有效返回但 Decision 不符合约定的情况存在再次决策路径；底层原生 Tool Call 解析直接抛错不等于一定会进入该修复路径，不能宣传“所有错误自动自愈”。

面试一句话：区别不在于“套了 Agent 框架”，而在于模型输出进入一个有业务边界、有状态、有动作校验的任务流程。

## 4. Tool Calling

### 当前 v2：10 个模型可选 Tool

来源：[companion-tools.ts](../../src/lib/agent/companion-tools.ts)。这些 Tool 使用 LangChain 的定义/转换能力生成供应商 Schema，但定义中的函数只是回传参数；实际业务由编排器根据 Decision 执行，不是让模型任意调用函数或直接写数据库。

前 8 个 Tool 共用可选字段：`dialogue_act`（new_task / answer / correction / feedback / cancel）、`clarification`、`knowledge_question`。`facts` 为可选对象，支持 `missing_material`、`available_materials_known`、`actual_materials`、`actual_steps`。所有对象受 Zod 严格校验，字符串长度、数组长度、枚举有边界；例如材料列表最多 30 项，但“合法字符串”不代表业务事实一定正确。

| Tool | 关键输入 | 用户场景、输出及价值 |
| --- | --- | --- |
| `find_recipes` | 必填 `materials: string[]`；可选 `category: classic/convenience/any` | 按材料找酒；输出找酒决策，业务侧返回真实配方卡或类别澄清，避免编造配方 |
| `open_recipe` | 必填 `recipe_name`；可选 `category` | 点名找酒；映射真实目录中的配方，不接受模型自造 URL |
| `explore_materials` | 必填 `materials` | 想探索材料组合；产生实验室交接动作，而非冒充经典配方 |
| `locate_feature` | 必填 `capability: recipe/substitute/lab/finder/records` | 不知道功能入口；生成固定能力范围内的定位/导航动作 |
| `change_recipe` | 可选 `materials`、`facts` | 缺料或想替换；进入咨询、其他真实酒单或参考实验室方案 |
| `guide_recipe` | 可选 `facts` | 询问当前配方怎么做；结合可信配方上下文提供引导/知识结果 |
| `troubleshoot_recipe` | 可选 `facts` | 已经做了但口感不对；必要时补实际材料和步骤，再解释 |
| `answer_knowledge` | 可选 `facts` | 知识类问题；触发规则知识或检索，得到带证据的回答或证据不足 |
| `clarify_request` | 必填 `clarification`；可选 `intent`、`dialogue_act` | 问题尚不能安全归类；输出必要的澄清，而不是盲目执行 |
| `reject_out_of_scope` | 可选 `dialogue_act` | 超出任务范围；明确边界 |

原始 Tool 输出是结构化 Decision；上述“卡片/知识/按钮”是编排后的产品结果。模型需恰好返回一个 Tool Call，未知名称、无效 JSON、多个调用或参数不合法会被拒绝。

### 确认、有效性与风险边界

- 查知识、匹配配方等只读步骤不逐个弹确认框。导航、定位、预填实验室由用户点击动作按钮触发，不由模型静默执行。
- 每个动作携带任务标识与版本，前端执行前核对当前会话；配方跳转必须能解析到真实目录，能力跳转使用固定枚举。
- 实验室交接有 5 分钟有效期；已有草稿时存在覆盖确认/冲突保护。交接材料用量还受前端传递协议校验。
- 预填可以给出明确标记为“参考”的建议用量，不能说“Agent 从来不给用量”。自动材料映射强调唯一身份，避免把柠檬茶当纯柠檬汁。
- 这些是当前应用内的 UX 和有效性控制，不是防恶意客户端的服务端事务授权。Agent 没有直接开放购买、发布知识、修改账户等高风险 Tool。

依据：[session](../../src/lib/agent/companion-session.ts)、[AssistantProvider](../../src/components/assistant/AssistantProvider.tsx)、[LabScreen](../../src/components/LabScreen.tsx)、[材料身份](../../src/lib/mixology/material-identity.ts)、[参考配方](../../src/lib/mixology/reference-experiment.ts)。

### 旧版本/辅助工具：不能混算成当前 v2 自主能力

| 链路 | Tool 与参数 | 输出/约束 |
| --- | --- | --- |
| v1 preparation，API 仍保留 | `read_recipe()`；`search_knowledge(question)`；`check_capacity(capacity,current,addition,evidence)`；`clarify(question)`；`finish()` | 读取上下文、知识结果、容量检查或结束；有受限循环和观察值。容量需对应用户明确提供的实际数值证据，不应拿标准配方量冒充实倒量 |
| legacy core，非当前主入口 | `find_recipes(query,omit)`；`check_recipe(recipeId)`；`search_knowledge(question)`；`finish(recipeIds,question)` | 候选、可制作性、知识、最终结果；只允许检查已发现配方并有限制地循环 |
| 联网供应商侧 | `web_search` | MiniMax 服务端搜索工具，不是上述 10 个业务 Tool 之一；结果还需应用侧校验 |

旧链路的 Tool 决策主要采用 JSON 协议，不应全部说成原生 Function Calling。管理员发布/撤回知识属于人工后台，不是 Agent 的写入 Tool。依据：[preparation](../../src/lib/agent/preparation.ts)、[legacy core](../../src/lib/agent/core.ts)、联网适配（历史文件 `minimax-search.ts`，现已退役）。

## 5. RAG

### 判断：有真实 RAG，但不是大规模文档知识平台

当前具有 embedding、PostgreSQL/pgvector 相似度检索、Top-K、证据组装、生成及引用校验，也有联网补充与人工审核实现。不能把它弱化成纯关键词查询，也不能夸成成熟企业知识治理系统。

| 问题 | 当前真实情况 | 依据 |
| --- | --- | --- |
| 知识来源 | 主向量种子为 50 条调酒避坑问答，包含标题、别名、回答、适用范围、来源、初始检查标记；另有饮食/技法规则知识，不等于都进入向量库 | [cocktail-pitfalls](../../src/lib/knowledge/cocktail-pitfalls.json)、[core](../../src/lib/knowledge/rag/core.ts) |
| 如何入库 | 导入脚本生成 embedding，完整成功后事务写入；种子与审核发布内容区分版本；校验并发期间已审核数据变化 | [rag 脚本](../../scripts/rag.ts)、[runtime](../../src/lib/knowledge/rag/runtime.ts) |
| Chunking | 一条结构化问答作为一条检索单元；有 chunk 数据表，但没有通用 PDF/长文解析、滑窗或语义切块流水线 | 同上 |
| Embedding | 默认配置模型名 `text-embedding-v4`，1024 维；HTTPS 端点、模型和密钥由环境配置。此处不声称已核验用户当前密钥/账户 | [providers](../../src/lib/knowledge/rag/providers.ts)、[环境样例](../../.env.example) |
| 向量库 | PostgreSQL + pgvector，`rag_chunks` 中 vector(1024) 与结构化数据 | [schema](../../prisma/schema.prisma)、[迁移](../../prisma/migrations/20260912000000_add_rag_chunks/migration.sql) |
| Similarity | 余弦距离算子转换相似度，过滤数据版本及 embedding profile；没有发现本迁移创建 ANN 索引 | [runtime](../../src/lib/knowledge/rag/runtime.ts) |
| 排序/Top-K | SQL 先取最多 100 条候选，再按语义分数与关键词信号加权；默认 Top-K=3，接口范围 1–5。不是训练式 reranker 或完整 BM25 混合检索 | [core](../../src/lib/knowledge/rag/core.ts)、[runtime](../../src/lib/knowledge/rag/runtime.ts) |
| Context | 问题与当前上下文参与检索；生成时提供命中文档的 id/title/answer/scope，及当前配方、用户问题等上下文。v2 传入检索的上下文截到 6000 字符，不是智能预算压缩 | [route](../../src/app/api/agent/route.ts)、[providers](../../src/lib/knowledge/rag/providers.ts) |
| Citation | 模型输出 claims + evidenceIds；校验引用 ID 来自本次证据，拒绝回答正文中的自造 URL，再从证据组装来源链接 | [core](../../src/lib/knowledge/rag/core.ts) |

向量 profile 包含端点、模型、维度等配置指纹，用来减少不同 embedding 空间混查。文档中“已检查来源”是项目数据标记，不代表全部经过调酒专家审核。

### 检索不足、联网与 Fallback

1. 先检索本地知识；常规相似度阈值默认 0.5，`searchAndCollect` 进一步使用关键词命中或语义分数至少 0.68 的强证据条件。
2. 本地强证据能形成有效回答，则直接返回，不为了增加内容而强行联网。
3. 没有足够证据或本地回答不能支持结论时，尝试受限联网。没有命中时可直接返回 `no_evidence`，生成无法支持答案时返回 `insufficient_evidence`。
4. 默认 MiniMax 搜索只接受能关联到真实服务端 `web_search` 调用的结果，不把模型正文中出现的链接当证据。可信域名范围包含 IBA、Difford’s Guide、Liquor.com、Suntory、Cointreau 等。
5. 默认联网证据主要是搜索摘要，不是完整网页抓取。另有 Tavily 适配分支；不能说已经部署全网爬虫或始终读完来源全文。
6. 无足够证据就保留不确定性、补充必要问题或安全停止回答；数据库/embedding/生成服务异常不等于“证据不足”，也不保证都会自动转联网成功。
7. Prompt 要求保留条件，不把“不等价”改写成“绝对不能替代”。引用 ID 校验只能验证来源归属，不能自动证明文本语义忠实。

依据：[searchAndCollect / 搜索流程](../../src/lib/knowledge/review/search.ts)、MiniMax 结果校验（历史文件 `minimax-search.ts`，现已退役）、[生成约束](../../src/lib/knowledge/rag/providers.ts)。联网来源分数中的占位值不是计算出的可信概率。

### 待审知识闭环

```text
本地知识不足 → 受限联网 → 有证据回答 / 明确不足
                         ↓ 尽力采集
                  gap 或 pending 待审记录
                         ↓ 管理员修改、核对来源
           发布 / 驳回 / 合并到已发布项
                         ↓
              发布项 embedding → 正式检索
                         ↓
                 撤回 → 移除正式向量
```

- 采集按规范化问题和配方上下文的精确指纹去重并累计出现次数，不是语义聚类或自动归纳。
- 状态包括 `gap / pending / published / rejected / merged`。发布要求回答、适用范围、来源和审核说明等；并非原封不动把搜索结果入正式库。
- 管理接口检查管理员权限；发布前生成 embedding，再通过事务、锁和 revision 检查防止覆盖他人更新，并写审核记录。
- 撤回从正式向量库移除，回到待处理状态；合并目标须为已发布项，主要处理记录关系/次数，不自动合成正确答案。
- “冲突”主要是并发版本冲突；知识内容是否互相矛盾仍需人判断，没有完整自动事实冲突检测。
- 联网回答可能在人工审核前展示给当前用户。人工审核控制的是进入正式知识库并供后续复用，不是所有实时联网回答都先经过人工。
- 采集写库失败时会记录警告，不一定丢弃已有回答；没有可靠消息队列和自动补偿闭环保证。

依据：[store](../../src/lib/knowledge/review/store.ts)、[review contract](../../src/lib/knowledge/review/contract.ts)、[管理 API](../../src/app/api/admin/knowledge/route.ts)、[审核页面](../../src/app/admin/knowledge/ReviewClient.tsx)、[审核迁移](../../prisma/migrations/20260915000000_add_knowledge_review/migration.sql)。实现及局部真实数据库验证存在，但尚不能证明最新版本已生产稳定运行。

## 6. Agent + RAG 整体流程

```text
用户在配方详情 / 实验室输入
→ 前端提交当前页面、近期对话、pending、taskId/version
→ API 鉴权、Schema、预算、超时
→ 重新核实真实配方上下文
→ 前置快捷规则 → L1 明确意图 → L2 任务续接 → 必要时 LLM Tool Calling
→ Router 分发：目录规则 / 功能动作 / 咨询澄清 / 规则知识 / RAG
→ 必要时：本地检索 → 证据回答 → 受限联网 → 待审采集
→ 组装结果与新的 pending / action
→ 前端检查任务和版本，只展示当前有效结果
→ 用户阅读、回答追问，或点击动作 → 实验室再校验交接与草稿冲突
```

### 场景一：材料不够，询问替代

在某杯酒详情说“没有橙味利口酒，能用橙汁吗？”：识别缺料及明确候选，核对当前配方要求；已有具体候选时优先讨论候选是否适合，不机械要求列出全部库存。知识回答需解释甜度、酒精及风味差异，不能把“不等价”直接说成“不能”；可以交接参考实验方案，但不冒充标准配方。

如果只说“没有橙味利口酒”且没有候选/库存，当前可能先展示共享主材料的其他真实酒单，不保证总是先追问库存。候选酒也不等于用户现有材料一定全部满足。依据：`consultation.ts` 的 `openAlternatives` 及 `companion.ts` 的候选分支。

### 场景二：连续追问同一杯酒

“这杯太酸了” → 记录正在排查当前配方 → 必要时问实际材料/步骤 → 用户补充后更新当前咨询事实，不重复询问已明确的信息。若换到另一杯或取消，旧 pending/异步按钮不再适用；同页新话题则仍要警惕近期历史影响。当前快捷调整规则与排查规则还有优先级冲突，见评测失败项，不能承诺所有追问都正确。

### 场景三：知识库证据不足

询问某种未收录材料是否能替代现有材料 → Router 进入知识路径 → 本地检索不满足强证据条件 → 受限联网 → 校验搜索来源 → 有支持证据才回答，否则显示证据不足。问题可进入待审记录，后续由管理员补充、审核并发布；“搜到网页”不等于“已解决问题”，也不等于“已进入正式知识库”。

## 7. Guardrail / 风险控制

| 机制 | 解决的风险 | 不能过度声称的边界 |
| --- | --- | --- |
| Prompt 约束范围、证据与条件 | 模型编造知识、扩大结论、不必要追问 | Prompt 不是可靠的事实验证器或完整防注入系统 |
| 严格 Tool Schema、单 Tool Call | 无效参数、未知动作、不可解释的批量执行 | Schema 合法不等于意图/事实正确 |
| 真实目录与身份回查 | 虚构配方、用错误配方解释当前页 | 实验室参考方案不是经典标准配方 |
| 固定导航枚举、目录 ID | 错误 URL、跳转到不存在的酒 | 需结合前端实际执行检查 |
| 用户点击、草稿覆盖确认 | 未经同意替换用户实验材料 | 只读检索没有逐次确认；前端确认不是服务端权限 |
| taskId/version、取消与配方键 | 迟到响应、旧按钮执行、跨配方状态污染 | 没有彻底语义隔离同页所有历史事实 |
| 引用 ID 与来源 URL 校验 | 伪造出处、引用未检索到的资料 | 不能证明结论被来源完整蕴含 |
| 明确 no_evidence / insufficient_evidence | 证据不足仍给确定建议 | 可能降低问题完成率，须评估合理拒答与过度拒答 |
| 鉴权、请求预算、超时、错误反馈 | 未登录滥用、并发重复、服务挂起 | 不代表已有完整线上 SLO、监控告警与成本台账 |
| 管理权限、revision、事务、审核日志 | 未审内容污染正式库、多人编辑覆盖 | 不自动判断内容真实性或知识冲突 |

预算默认包括每分钟、滚动日与并发限制；API 总请求时限与模型/检索子请求时限分层配置。此处是实现层面的保护，不宣称线上容量已压测。详见 [request-budget-runtime](../../src/lib/ai/request-budget-runtime.ts)、[API](../../src/app/api/agent/route.ts)、[backend-operations](backend-operations.md)。

实验室存在参考用量和调整启发式，但没有端到端证明“所有建议均不会溢杯”的安全系统。不要把旧 preparation 的容量工具扩展宣传为当前 v2 对所有建议都进行严格容量验证。

## 9. Failure Cases

下面区分真实模型回放、历史记录、离线回归复现和当前未解决失败。它们不是生产事故统计；没有旧日志的案例，不虚构用户投诉或修复前线上发生次数。

### 1. 材料找酒误路由成风味探索

- 用户输入/场景：给出现有材料，想看经典和便利店可做酒单。
- 原本错误行为：进入探索/实验室语义，而不是按真实目录找酒。
- 根因：材料组合既可表达“找现有配方”也可表达“自由创作”，仅由模型判断边界不稳定。
- 修改方案：加强明确找酒规则及模型决策后的意图约束，把点名、材料找酒与探索区分。
- 修改后结果：历史 companion 7 场景从 5/7 到 7/7；当前另有路由离线断言。不能据此证明所有自由表达都正确。
- 依据：[初次报告](../../artifacts/evaluations/companion-2026-09-16T02-56-03-868Z.json)、[后续报告](../../artifacts/evaluations/companion-2026-09-16T03-04-49-022Z.json)、[intent-funnel](../../src/lib/agent/intent-funnel.ts)。

### 2. 点名配方仍追问类别

- 用户输入/场景：明确点名 Highball 等真实配方。
- 原本错误行为：仍要求先选择类别，打断明确任务。
- 根因：类别消歧逻辑压过了“已经有唯一真实目标”的优先级。
- 修改方案：明确酒名优先，统一目录匹配/别名与去重后返回真实配方。
- 修改后结果：对应历史 7 场景复测通过，当前有点名查找测试；跨类别所有同名情况仍需按实际目录检查。
- 依据：上述 companion 报告、[workflow-catalog](../../src/lib/agent/workflow-catalog.ts)、[companion.test](../../src/lib/agent/companion.test.ts)。

### 3. 任务切换后仍错误澄清

- 用户输入/场景：已有咨询任务时，转而问过滤等知识问题。
- 原本错误行为：不必要地继续澄清领域/任务，而未直接回答新知识需求。
- 根因：待续接状态与新任务识别的边界不充分；这是历史任务切换误处理证据，不等于已经证明全局数据串号。
- 修改方案：识别新任务/知识诉求，增加决策后的澄清约束，不机械沿用旧 pending。
- 修改后结果：对应局部复查通过；不是全量多轮组合通过证明。
- 依据：[意图回放](../../artifacts/evaluations/response-policy-live-intent.json)、[复查](../../artifacts/evaluations/response-policy-live-intent-recheck.json)、[consultation](../../src/lib/agent/consultation.ts)。

### 4. 已说实际制作过程，还重复追问

- 用户输入/场景：用户描述已倒入的材料和操作，继续询问制作问题。
- 原本错误行为：再次问材料，或追加并非当前解释必须的用量问题。
- 根因：实际事实未充分提取/复用；澄清策略把“字段不全”当成“不能回答”。
- 修改方案：提取用户已陈述的实际材料和步骤，按当前问题最小充分信息决定是否追问。
- 修改后结果：[最终单案例](../../artifacts/evaluations/response-policy-live-trouble-final.json) 通过；不能替代全部排查回归。当前仍有快捷调整抢占排查的失败。
- 依据：[clarification-policy](../../src/lib/agent/clarification-policy.ts)、[consultation](../../src/lib/agent/consultation.ts)、响应策略回放。

### 5. 引用是真的，结论却被扩大

- 用户输入/场景：橙汁是否能替代橙味利口酒。
- 原本错误行为：将来源中的“不等价”表达成绝对不能替代。
- 根因：引用 ID 合法只说明用了该条来源，不能保证生成结论忠实保留条件。
- 修改方案：加强生成约束，区分经典等价替换与风味实验；关键结论无证据则不足回答。
- 修改后结果：后续诊断返回证据不足而非强行给结论。此结果证明安全停止，不证明用户替代问题已经被解决。
- 依据：[live-search](../../artifacts/evaluations/response-policy-live-search.json)、[recheck](../../artifacts/evaluations/response-policy-live-search-recheck.json)、[providers](../../src/lib/knowledge/rag/providers.ts)。

### 6. 向量有近邻，但没有真正答案

- 用户输入/场景：某种西柚啤酒/材料缺失后的替代问题。
- 原本错误行为/不足：检索得到语义相近但不足以支持具体替代的资料，联网后仍没有充分证据，用户任务未完成。
- 根因：相似度不是可回答性；小知识库对具体产品替代覆盖不足，串行检索/生成/联网还会增加等待。
- 修改方案：强证据过滤、弱命中避免无效本地生成；明确候选时聚焦候选，无候选时可引导其他真实酒单。
- 修改后结果：当前有弱证据路径离线覆盖；历史回放仍有证据不足，尚无最新全链路修复成功证明。
- 依据：联网回放、[search](../../src/lib/knowledge/review/search.ts)、[review.test](../../src/lib/knowledge/review/review.test.ts)。

### 7. 配方身份不一致：冰块被液体材料视图遗漏

- 用户输入/场景：用户指出当前配方写了冰块，助手却按不完整材料上下文判断缺料。
- 原本错误行为：配方呈现与咨询判断不一致，容易反复争论“原配方是否需要”。此项以文档记录和离线回归为证，不包装成生产事故。
- 根因：实验室液体材料视图不能代表完整配方要求，辅料/可选项需要单独表达。
- 修改方案：引入完整 recipe requirements，按配方身份回查，并区分必需/可选辅助材料。
- 修改后结果：会话修复回归包含相关检查；无对应最新真实模型整链路证明。
- 依据：[响应规范](agent-response-guidelines.md)、[recipe-requirements](../../src/lib/agent/recipe-requirements.ts)、[conversation-repair.test](../../src/lib/agent/conversation-repair.test.ts)。

### 8. 替代候选与真实材料身份混淆

- 用户输入/场景：提出明确替代候选，或将柠檬茶等饮料带入实验室。
- 原本错误行为：候选被误当库存/反复索要材料；模糊匹配可能把含某风味的饮料当成纯原料。证据是当前修复说明与离线复现，不是历史线上次数。
- 根因：候选、持有、实际倒入是不同事实；字符串包含关系不能证明材料相同。
- 修改方案：分离 replacement 与 available facts；自动参考映射只接受唯一身份/别名，不能仅靠风味子串。
- 修改后结果：相关会话修复断言通过；参考用量仍只是启发式建议，不代表口感已实测。
- 依据：[consultation](../../src/lib/agent/consultation.ts)、[material-identity](../../src/lib/mixology/material-identity.ts)、[conversation-repair.test](../../src/lib/agent/conversation-repair.test.ts)。

### 9. 旧 Agent 反复调用同一个知识 Tool 直到超时

- 用户输入/场景：“我不知道该加多少冰”。
- 原本错误行为：旧 Agent 在证据不足后多次重复 `search_knowledge`，最终 timeout。
- 根因：任务规划未将“当前证据不足，需要补上下文”有效当作停止条件。
- 修改方案：知识场景更直接地检索并返回必要澄清，限制循环和重复调用；当前 v2 也不采用开放式任意工具循环。
- 修改后结果：历史复查同题返回 `insufficient_evidence` 并询问配方/杯型，而非反复搜索。是旧版本改进证据，不是当前所有 Tool 失败自动恢复的证明。
- 依据：[首次技法回放](../../artifacts/evaluations/technique-regression-first-attempt.json)、[复查](../../artifacts/evaluations/technique-regression.json)、[legacy flow](../../src/lib/agent/flow.ts)。

## 10. 产品取舍

- **为什么规则优先？** 用户明确意图、真实配方、取消和入口操作可以确定性处理。收益是可控、可解释、少一次模型调用；代价是规则增长和优先级冲突，当前失败已经说明这一点。
- **为什么 Agent 而不是普通 chatbot？** 任务要承接页面、保存待补信息并把结果带入实验室，而不是只给一段文本。这里是窄任务 Agent，不需要为了“Agent”标签增加自主循环。
- **为什么需要 RAG？** 解释替代和技法时需要来源与适用条件；Prompt 本身不提供外部证据。RAG 也不保证答案正确，需要检查可回答性与语义忠实度。
- **为什么不是全部联网？** 可信本地知识更稳定、成本和延迟可控；联网覆盖长尾，但摘要可能不足、来源不一致且依赖服务稳定性。没有线上数据证明当前策略已达到最优。
- **为什么联网内容不能直接正式入库？** 单次搜索可能脱离配方上下文，有错误、重复或过度概括；审核是控制未来复用污染。当前用户仍可能先看到有来源的实时回答，应持续改进实时风险边界。
- **如何平衡成本、延迟、准确率、灵活性？** 规则处理确定请求；复杂口语交模型；知识先本地再按需联网；不足则澄清/拒答。默认 Top-K=3 是当前实现选择，不是已经充分调参得出的最优值。
- **最大的 limitation？** 当前仍依赖手写优先级与小样本验证；原生 Tool Calling、规则直答、缺料交接迭代后没有同一快照的完整真实链路回归。不能用分散历史通过报告替代产品整体可靠性。

## 12. 面试高频追问

以下共 30 题。回答采用“用户问题 → 选择 → 实现证据 → 边界”的顺序；30 秒先讲判断，1 分钟再用一个案例展开，不需要背诵库名。

### 产品问题

#### Q01 为什么选择这个场景，用户是谁？

- **30 秒：** 面向家庭调饮成年新手，核心困难不是缺一篇百科，而是不知道当前材料、当前配方和实际操作怎么衔接。
- **1 分钟：** 说明找酒、缺料、制作求助三个时刻，展示助手为何放在详情/实验室；承认画像来自产品假设，下一步应访谈和观察任务过程验证频次。
- **考察：** 是否从用户问题出发；不要把假设说成调研结论。

#### Q02 MVP 为什么做这些，不做什么？

- **30 秒：** 先打通真实配方到制作求助，目录与计算用规则，口语与证据解释用 AI，不做全自主代操作。
- **1 分钟：** 用“按材料找酒”和“缺料替代”说明核心路径，解释入口收敛；OCR、开放式网页操作、长期个性化当前不作为已实现能力。
- **考察：** 范围管理和价值优先级，而不是功能数量。

#### Q03 与直接问通用聊天产品有何区别？

- **30 秒：** 当前助手知道用户正在看哪杯酒，输出能关联真实目录和可点击动作，还能续接问题与预填实验室。
- **1 分钟：** 讲缺料案例：核对当前配方要求、判断是否需追问、查证据、用户确认交接；再说明这是场景闭环优势，尚无用户对比实验验证体验领先。
- **考察：** 场景壁垒与可验证差异，不是泛谈模型更聪明。

#### Q04 如何衡量产品是否有价值？

- **30 秒：** 应看用户是否完成找酒/缺料决策/制作任务，以及无效追问、错误建议和放弃，而不只看对话次数。
- **1 分钟：** 分任务定义完成事件，记录路由、动作采纳、退出、证据不足及等待时间；项目已有基础 analytics，但这些 Agent 成效指标尚未形成可靠线上闭环。
- **考察：** 指标定义及诚实区分已有数据与未来测量方案。

### Agent 问题

#### Q05 这到底算不算 Agent？

- **30 秒：** 是有上下文、任务状态和受控工具路由的轻量 Agent，不是单纯聊天，也不是自主规划系统。
- **1 分钟：** 沿输入、规则漏斗、必要时单 Tool Call、业务执行、pending 更新、用户动作解释；强调主要价值在任务承接与约束，不在循环次数或框架名。
- **考察：** 架构理解；不要宣称多 Agent 或复杂自治规划。

#### Q06 Router 如何判断意图？

- **30 秒：** 明确请求先规则，待续接任务再规则，仍不确定时由模型选择结构化 Tool；不是每轮都分类模型调用。
- **1 分钟：** 点名配方直接查目录；回复类别沿 pending 续接；模糊问题进入 Tool Calling；指出前置 adjustment 等快捷规则也存在，优先级需统一治理。
- **考察：** 能否解释真实控制流及冲突，而不是只画理想架构。

#### Q07 多轮任务如何续接？

- **30 秒：** 提交当前页面、近期历史和显式 pending，记录缺料、待补材料/步骤等阶段；不只依赖模型“记住”。
- **1 分钟：** 说明 recipeKey、替代候选与真实库存的区别，怎样跳过已明确的信息；强调近期窗口有上限、没有持久用户记忆和完备事实溯源。
- **考察：** 状态设计与数据语义，PM 层面能说清字段用途即可。

#### Q08 如何处理任务切换与取消？

- **30 秒：** 取消请求、清 pending 并提升版本，页面切换后旧结果和旧按钮失效；新任务不机械接旧咨询。
- **1 分钟：** 举上一杯请求慢返回的例子，解释 taskId/version；再说明前端检查不等于服务端持久会话授权，同页历史仍有潜在干扰。
- **考察：** 异步交互和边界意识，避免宣称绝对隔离。

#### Q09 用户纠正 Agent 时怎么做？

- **30 秒：** 对配方事实重新查可信目录；对实际制作事实采纳用户描述，但区分实际、候选和标准配方。
- **1 分钟：** 用冰块要求和橙汁替代举例：不能盲从“原配方就是这样”，也不能否认用户已经倒入的材料；必要时问最少的澄清问题。
- **考察：** 事实优先级、可纠正性与体验设计。

### RAG 问题

#### Q10 为什么需要 RAG，Prompt 不够吗？

- **30 秒：** Prompt 约束行为但不提供可靠外部知识，RAG 提供可追溯证据与适用范围。
- **1 分钟：** 举替代问题，说明来源和条件为何重要；同时承认真实引用仍可能被模型错误概括，因此 RAG 是减少风险，不是消除幻觉。
- **考察：** 是否理解检索与生成各自的作用。

#### Q11 你的知识库怎么构建、怎么切块？

- **30 秒：** 主种子是 50 条结构化调酒问答，一条作为检索单元；审核发布内容也能进入向量库，没有通用长文切块管线。
- **1 分钟：** 介绍标题、别名、答案、scope、来源如何生成 embedding，导入事务与版本；饮食/技法直答知识需区别于向量语料。
- **考察：** 数据来源及实际工程边界；不要背不适用的 chunk size。

#### Q12 检索如何工作，为什么 Top-K=3？

- **30 秒：** 使用 1024 维 embedding 与 pgvector 余弦检索，再加关键词信号筛选，默认给生成器 3 条证据。
- **1 分钟：** 解释 K 太小会漏证据、太大会引入噪声和成本；当前值是实现默认，不是充分调参结论，未来应用标注集比较召回与回答正确性。
- **考察：** 检索权衡；无需手写向量公式，但必须理解相似不等于可回答。

#### Q13 如何保证引用可信？

- **30 秒：** 引用 ID 必须来自本次命中，链接由原始证据组装，模型不能自己写一个 URL 当依据。
- **1 分钟：** 分开“来源存在”“来源可信”“支持结论”三个层次；用橙汁不等价被写成不能替代的失败说明当前缺少强语义忠实校验。
- **考察：** 是否把形式校验误当事实正确。

#### Q14 本地没有答案怎么办？

- **30 秒：** 按强证据条件判断，必要时受限联网；仍无支持就明确不足，不强答。
- **1 分钟：** 说明域名、真实搜索调用与摘要边界；服务错误和知识不足应分开，不能把超时包装成“确实没有答案”。
- **考察：** Fallback 是否具体且可观测。

#### Q15 联网知识如何进入知识库？

- **30 秒：** 搜索结果进入 gap/pending，人工核对并编辑后发布；有 revision、审计记录和撤回向量机制。
- **1 分钟：** 解释实时回答与未来复用分开，精确指纹去重不是语义学习，合并不是自动合成知识；采集失败没有可靠补偿队列。
- **考察：** 知识治理，不要宣传成模型自动学习或持续训练。

### Tool Calling 问题

#### Q16 Function Calling 与普通 JSON 回答有什么区别？

- **30 秒：** 当前 v2 向供应商注册 Tool Schema 并解析 tool_calls；旧链路主要让模型输出 JSON 决策，两者都需要应用层执行和校验。
- **1 分钟：** 说明恰好一个 Tool、名称和参数检查、Decision 到业务逻辑的映射；原生调用格式仍可能出错，不保证意图正确。
- **考察：** 能否分清协议、模型选择、实际执行三个层次。

#### Q17 为什么不让 Agent 自动执行所有动作？

- **30 秒：** 找知识可以自动读，但改变用户草稿会影响实际操作，需要用户理解并确认。
- **1 分钟：** 按只读、导航、预填、正式数据写入分风险；当前模型不直接发布知识或修改账户，预填通过按钮且有草稿保护。
- **考察：** 风险分级与人机控制，而不是笼统说所有操作都要确认。

#### Q18 如何防止旧按钮误操作？

- **30 秒：** 按钮绑定 taskId/version，当前任务不匹配就不能执行，实验室交接另有 5 分钟有效期。
- **1 分钟：** 举切换酒款或取消后的旧建议；说明过期判断与草稿冲突是不同问题，也不等于后端不可伪造的权限系统。
- **考察：** 状态有效性与异步风险。

#### Q19 参数合法就能放心执行吗？

- **30 秒：** 不能。Schema 验证格式，目录验证身份，用户确认与状态检查验证当前动作是否适用。
- **1 分钟：** 用合法字符串“柠檬茶”却不能当“柠檬汁”说明语义风险；枚举、真实 ID、唯一材料映射和证据约束分别补不同层面的校验。
- **考察：** 多层 Guardrail 的分工。

### Evaluation 问题

#### Q20 评测体系如何分层？

- **30 秒：** 离线保证确定性逻辑，浏览器保证展示和交互，真实模型/服务回放观察模型及外部依赖表现。
- **1 分钟：** 各举一个：旧按钮失效、页面点击交接、模型意图误判；说明 Mock 不能替代真实全链路，历史报告不能替代当前快照回归。
- **考察：** 测试目的和覆盖边界。

#### Q21 目前到底通过了多少？

- **30 秒：** 当前离线执行 152 项，150 通过、2 失败，类型检查通过；真实模型有历史 7/7，但不是当前全链路成绩。
- **1 分钟：** 解释顶层与嵌套计数、浏览器 fixture、真实评测中的规则旁路；明确不把所有不同版本相加成一个准确率。
- **考察：** 数字诚信与统计口径。必须能指出当前两项失败。

#### Q22 如何判断 RAG 好不好？

- **30 秒：** 分开检索是否找对证据、回答是否被证据支持、该拒答时是否拒答，不能只看有引用。
- **1 分钟：** 历史测试集的 Recall@3/MRR 有明确相关证据分母；再补任务完成、过度拒答、延迟。小样本满分不等于泛化准确率。
- **考察：** 指标与用户价值的对应关系。

#### Q23 测试挂了怎么判断改代码还是改测试？

- **30 秒：** 先明确期望的产品行为，再看实现与断言谁偏离，不能为了变绿放松校验。
- **1 分钟：** 对 adjustment 抢占排查检查必要信息和优先级；对技法直答检查是否允许跳检索、答案是否有可信依据，再更新测试与全链路回归。
- **考察：** 规格治理和失败处理的判断力。

### 技术理解问题

#### Q24 embedding、向量库和 LLM 分别做什么？

- **30 秒：** embedding 把文本转成可比较表示，向量库找到相近资料，LLM 根据资料组织回答；不是把知识直接训练进模型。
- **1 分钟：** 说明本项目 profile 防不同向量空间混查、pgvector 做检索、证据 ID 连接生成结果；相似度不能直接解释成正确概率。
- **考察：** PM 是否能与研发讨论链路，无需推导底层数学。

#### Q25 如何考虑成本和延迟？

- **30 秒：** 确定请求走规则，本地知识优先，联网按需，限制上下文和请求时间；当前没有完整线上成本改善数据。
- **1 分钟：** 拆解意图模型、embedding、数据库、生成、联网的串行耗时，提出记录每步调用/用量及用户等待；有 trace 不等于已有精确成本核算。
- **考察：** 可落地的预算和体验取舍，不要虚构降本百分比。

#### Q26 数据库与状态各存在哪里？

- **30 秒：** 向量和审核数据在 PostgreSQL；当前对话主要由前端会话携带，实验室交接有临时存储，不是所有数据都在一个长期记忆库。
- **1 分钟：** 区分真实配方目录、业务记录、向量知识、待审状态与临时 pending；解释为什么客户端任务版本不能替代服务端鉴权。
- **考察：** 系统边界和数据责任，PM 层面说清生命周期即可。

### 失败案例与复盘问题

#### Q27 最有价值的一次失败是什么？

- **30 秒：** “不等价”被说成“绝对不能替代”，虽然引用合法，仍然给出了超出证据的结论。
- **1 分钟：** 还原输入、错误、形式校验盲区、Prompt 条件约束与不足回答；最后承认复查的安全拒答不等于任务完成，下一步应补语义忠实评测。
- **考察：** 能否从个例提炼评测缺口，且不美化修复结果。

#### Q28 如何复盘上下文污染？

- **30 秒：** 先区分跨配方 pending、同页旧偏好、异步旧结果和新任务误续接，不笼统归为模型记忆不好。
- **1 分钟：** 说明 recipeKey、task version、取消后历史截断分别处理什么；举历史新知识仍澄清案例，承认同页事实隔离尚不完整。
- **考察：** 根因拆解和机制与故障一一对应。

#### Q29 知识库不足时，应该继续优化模型吗？

- **30 秒：** 先判断是没召回、有资料但不支持、生成失真，还是服务失败；没有证据时换大模型不一定解决。
- **1 分钟：** 以替代问题说明补知识/改检索/聚焦候选/引导其他酒单的不同收益；保留拒答，衡量其是否帮助用户继续任务。
- **考察：** 是否把产品问题全部归因模型能力。

#### Q30 如果做 2.0，你优先改什么？

- **30 秒：** 先解决当前路由冲突并建立同版本完整回归，再用真实任务观察验证价值，而不是立刻上多 Agent。
- **1 分钟：** 排序讲任务成功定义、统一状态规则、证据忠实度、真实链路测试、延迟与知识运营；为每项说明验收方法，不给没有数据支撑的效果承诺。
- **考察：** 优先级、资源意识及对现状的准确判断。

## 13. 当前项目 Limitations & 下一步

### 如实承认的限制

1. **用户证据弱于实现证据。** 有产品设计和完整模块，不等于有真实高频需求、留存和商业验证。
2. **规则组合复杂。** 快捷分支、意图漏斗与多轮咨询仍有优先级冲突；混合任务不是完整任务分解。
3. **记忆有限。** 当前是窗口历史 + 显式 pending，没有长期用户记忆或完备事实隔离；任务版本主要在前端生效。
4. **知识与引用有边界。** 小型问答库、联网摘要、来源覆盖有限；合法引用不保证语义忠实，审核也不等于专家认证。
5. **验证存在版本断层。** 最新离线有两个失败，浏览器/模型/数据库报告分属不同日期；真实评测脚本与 API 搜索路径不完全相同。
6. **实验方案是参考。** 材料与用量启发式未经过广泛口感实验或完整容量安全验证，不是专业调酒保证。
7. **运营成熟度不足。** 有日志、预算和基础 analytics，但缺完整任务成功监控、成本归因、知识采集重试和稳定生产运营证据。

### 2.0 最值得优化的 5 个方向

| 优先方向 | 为什么值得做 | 建议验收方式，均为未来计划 |
| --- | --- | --- |
| 1. 用户任务验证与 MVP 收敛 | 先证明主要问题与完成价值，避免继续堆功能 | 观察真实用户完成找酒/缺料/制作任务，记录卡点、完成条件与退出原因 |
| 2. 统一 Router 与事实状态 | 当前失败直接暴露规则优先级与信息语义问题 | 明确新任务/续接/纠错优先级，区分标准、持有、候选、实倒；修复现有失败并补组合回归 |
| 3. 提升证据可回答性与忠实度 | 检索到不等于能回答，有引用不等于正确 | 标注替代条件、反例和不足样本；分别测召回、条件保留、错误断言与过度拒答 |
