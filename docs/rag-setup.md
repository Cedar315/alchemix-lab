# RAG 设计与知识维护

更新：2026-09-14。当前 RAG 已有实现；已接入悬浮助手；专项知识完整覆盖与人工忠实性仍待验证。

## 1. 产品职责

RAG 回答制作知识、替换依据和故障解释。配方推荐、页面导航和实验室计算使用业务功能，不通过语义检索替代。检索到材料替换资料也不代表可承诺精确等量、原味不变或适用所有品牌。

知识来源：[cocktail-pitfalls.json](../src/lib/knowledge/cocktail-pitfalls.json)。当前包含 50 个条目；每条作为一个检索单元，包含标题、别名、分类、答案、适用范围、检查日期、审核状态、证据类型及来源链接。`source_checked_initial` 不等于已完成人工专业审定。

饮食与饮酒限制另存于 [dietary-knowledge.json](../src/lib/knowledge/dietary-knowledge.json)，目前收录乳糖不耐受、牛奶过敏和孕期饮酒三条带来源的基础判断。悬浮助手对明确的“这杯能喝吗”问题直接读取这些条目，结合当前酒单材料回答，并在产品成分未知时要求核对标签。这三条暂不进入向量索引；后续如要合并入 RAG，须与应用版本一起重建并发布索引。

### 知识类别、场景与检索触发

以下按产品场景归组，不新增知识文件的 category 枚举。现有条目包括技法、冰与稀释、材料辨识、经典配方等分类；每个问题仍须验证命中文档实际支持的范围。

| 知识类别 | 用户场景 | 检索触发条件 | 预期展示 | 不足时处理／验收 |
| --- | --- | --- | --- | --- |
| 材料辨识与替换条件 | “这杯缺某种材料，可以换吗？” | 已确认缺料项和手边材料，站内酒库仍不能支持完整建议 | 有依据的选项、差异、适用条件及来源链接，保留快捷入口 | 站内不足再联网；没有可靠比例不补数字；A08、A09 |
| 制作技法与工具 | “这一步怎么过滤？” | 需要知识解释而非查找页面按钮 | 操作说明、适用器具和依据 | 缺必要事实问一项；A10、A21 |
| 冰与稀释 | “这杯应该加多少冰？” | 当前配方仍不足以直接说明制作方法 | 资料支持的做法与条件 | 不把缺杯型误识别为选酒；A10 |
| 甜度与混合现象 | “已经混好了，为什么分层？” | 先确认实际材料与操作，再检索 | 可能原因、补救建议与来源链接 | 已知不重复问；站内不足再联网；A20 |
| 经典配方说明 | “原版为什么用这种材料？” | 询问知识，而非打开酒单 | 依据来源解释原版要求与差异 | 不替代真实配方数据库；A21 |
| 其他已收录知识 | 询问条目覆盖的具体问题 | 符合产品范围且确有相关资料 | 在条目 scope 内回答并引用 | 不把库中有相近词当充分依据；A15 |

用户仅问功能位置、指定酒单或材料可做什么时，先调页面能力或配方匹配，不以 RAG 返回路由或候选。混合问题只将其中知识事项交给检索；失败不能抹掉已完成的有效事项。

### 资料来源与内容审核

知识文件保存来源标题和链接，不自动采信用户输入中的新链接。新增资料先确认其支持的论断，再写答案与 scope；标记直接依据或综合说明，并记录日期和审核状态。当前资料不构成对所有替换、品牌与具体场景的完整覆盖。

审核人员需检查“来源是否支持答案”“条件是否适用”“是否遗漏不确定性”。来源合法性由程序检查，语义忠实性仍需人工评审。本文只规定维护流程，不新增调酒事实。
## 2. 当前检索与生成

1. 对知识文件计算 datasetVersion；对嵌入 endpoint、model、1024 维计算 embeddingProfile。
2. 入库时嵌入标题、别名、分类、答案、scope；每批 10 条。
3. 检索前检查匹配版本与配置的行数是否等于文档数，否则返回 INDEX_NOT_READY。
4. 问题与背景一起嵌入，数据库按余弦相似度取最多 100 条。
5. 默认语义阈值 0.5；精确标题／别名命中也可进入候选。重排为 0.85 × 语义分 + 0.15 × 关键词分，再取 topK。
6. 无候选不调用答案生成模型。有候选则要求按证据生成 claims 和 evidenceIds，返回可校验引用。

别名命中与阈值只是检索策略，不能当答案置信度。需要用独立问题集校准，避免把训练／调参样本当验收集。当前小数据量使用精确查询，无须宣称具有大规模检索性能。

## 3. 答案边界

状态为 answered、insufficient_evidence、no_evidence。程序校验结构、证据 ID 和来源链接，拒绝伪造引用；这只能保证引用合法，不能保证每句推断忠实。生成时不联网搜索，也不实时检查来源页面变化。

知识更新应检查来源支持程度、适用条件、品牌差异和不确定措辞。direct 表示直接支持，synthesis 表示综合说明；综合不能冒充直接来源结论。没有可靠精确比例时保留限制，不让模型填数字。

### 回答状态与用户反馈

| 检索／生成情况 | 处理策略 | 用户展示 | 验收 |
| --- | --- | --- | --- |
| 资料足够且适用 | 按证据生成并校验 | 回答、必要限制、来源 | A10、A20、A21 |
| 找到资料但不足以支持完整结论 | 只给已支持部分，缺关键事实才追问 | 明确哪些不能确定 | A09、A15 |
| 成功检索但无相关资料 | 不调用答案生成模型 | 未找到相关依据 | A15 |
| 索引版本不一致或查询失败 | 记录技术错误，不假装无知识 | 知识更新中或查询未完成的状态 | A16 |
| 输出结构或引用不合法 | 不展示不可信答案 | 对应失败提示并允许重试 | A15、A16 |

具体固定话术见 [回复规范](agent-response-guidelines.md)，运行错误定位见 [后端手册](backend-operations.md)。
## 4. 配置和操作

必需：RAG_EMBEDDING_API_KEY、RAG_EMBEDDING_URL（完整 HTTPS embeddings 地址）、RAG_EMBEDDING_MODEL；答案复用 MINIMAX_API_KEY、MINIMAX_API_URL、MINIMAX_MODEL。维度固定为 1024，换模型先确认支持。`.env.example` 是示例，不保证账户当前开通对应模型。

```bash
npm run rag:status
npm run rag:ingest
npm run test:rag:live
npm run eval:rag
```

status 只读数据库；ingest 调用嵌入并替换索引，有费用和写入；live/eval 调用真实提供商并产生费用。完整环境、权限与排障见 [操作手册](backend-operations.md)。

入库先完成全部向量，再在事务和锁内替换 rag_chunks。失败应保留旧事务数据；成功后的旧应用版本可能因版本不一致不能检索。回滚必须同时对齐代码知识文件、嵌入配置和索引，不能只回退前端。

## 5. 知识治理与验收

每次变更记录修改原因、来源、适用范围、审核人或待审核状态，并跑 schema、离线检索规则、真实召回和人工忠实性审查。管理员接口 `/api/admin/rag` 仅用于受控维护，大批入库优先 CLI，避免超出路由运行时限。

新方案需补齐和审查“当前酒缺料”“哪些情况应回到已有替换功能”“实际制作与配方不同”“故障事实不足”等样本。已有 50 条不等于覆盖所有目标场景。历史 8 条召回结果见 [验证记录](agent-verification.md)，不能当作整个知识库正确率。
